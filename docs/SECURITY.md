# Security

Galahad is an autonomous agent with access to every machine you own, so its security is part of its design. This page records what it defends against, what an independent review found, and the limits that remain. Tested claims are marked as tested.

## Threat model, in one breath

**Defended against:**
- a stolen or lost device
- a stolen node key
- a prompt-injected agent (arm)
- hostile content in web pages, files and messages
- a compromised sandbox
- a malicious peer on your tailnet
- network partitions, clock skew, and duplicated or reordered delivery

**Out of scope:**
- an attacker who is already root on a full node, which holds the vault by design
- your Tailscale control plane being compromised, which is mitigated, not eliminated, by device-key signatures on every request

## Hivemind squires

Squires share Galahad's identity and knowledge while retaining attributable execution identities. Squires conversations, task state, VM bindings and working notes live in the controller's private `team.db`; this database is not replicated. Explicit `remember` calls write agent-trust entries to the existing signed shared mind. Room messages, predecessor results and notes enter model context as fenced data, never as new permissions.

Avatar profiles are cosmetic, versioned data: fixed enums and six-digit hex colors, with no user SVG, markup, URLs or file paths. The browser renderer uses fixed DOM geometry and treats labels as text; malformed or future profiles fall back to a deterministic default. Expressions come from job state, not model-generated markup or instructions. Avatar changes grant no capabilities and do not alter squire budgets or behavior.

- Squires reads require an owner client/admin plus the route's scope. Configuration, posting and task controls require `fleet:admin`; external arms cannot call these routes. The controller's in-process squires receive `mind:read`, `mind:write`, `sandbox` and `connect`, with a fixed tool allowlist, no bank access and no authority to change scopes, providers or budgets. `team.*` arm names are reserved; tokens minted under that prefix by older versions are rejected and must be reminted under an ordinary external name.
- Speaker identity comes from the controller, never model input. Room membership is checked for sends and delegation. A causal chain keeps the same budget across rooms and DMs, and each claimed delivery/task consumes one squire daily turn. These are **job counts, not token or money ceilings**. A job can make multiple model/tool calls. Concurrency, deadlines and action limits are separate bounds.
- Galahad may make squires of his own and write to them, and only that. In the owner's conversation he does it through three tools of his own (`team`, `team_recruit`, `team_message`); a squire does it for its room through the broker. The routes behind his tools accept the in-process principal `arm:galahad` alone, and only while he answers the owner on a device that holds `fleet:admin` itself: what a device may not do in Squires, he does not do for it, a fleet node is not the owner, and a turn that has these tools is steered only from a device that could command Squires (others may watch or stop it). A minted arm can never hold that label, and a token stored under it by an older version no longer authenticates, so no external agent, loop or node reaches them whatever its scopes; the tools are not offered over MCP. He can only add: an existing handle is refused, and he cannot edit, pause, re-brief, re-budget or provision any squire. A squire he makes gets the same fixed scopes and allowlist as any other, the default daily allowance, the native harness and a seeded avatar. He cannot give it a repository: a repository lease clones with the owner's GitHub access, which only the owner grants. Making is capped at 8 a day across him and his squires, inside the node's 32; his own messages at 40 a day; and each message or squire spends the same chain and daily allowances as the owner's would. Provenance is recorded and not his to set: `createdBy` and `instructionsBy` come from the calling identity, never from model input. A job he wrote enters the squire's context fenced, as his brief and explicitly not the owner's instructions, until the owner changes its words. A new squire's name is held to one plain word in its ordinary letter forms, since a model chose it and every briefing reads it. It must be written in one script, and one of a fixed list (Latin, Cyrillic, Greek, Armenian, Georgian, Cherokee, Hebrew, Arabic, the main scripts of India and south-east Asia, and Chinese, Japanese and Korean writing together), with nothing in it that is written but never drawn. It is refused if it would be taken for `you`, `owner`, `system` or `Galahad`, or for another squire's name (one that was removed included), however it is spelled: a letter of another script drawn like a Latin one, in either case; small capitals; Latin letters with a hook, bar or stroke; a capital I or a 1 for an l; a 0 for an o; `rn` for `m`, `cl` for `d`; an accent, a hyphen, a raised apostrophe (`packages/core/src/lookalike.ts`). That table is 140 letters of the scripts drawn like Latin, not Unicode's whole list of confusables: a look-alike within another script (two similar Han or Arabic letters) is not found, and a script that is not on the list is refused outright rather than vouched for. Names the owner gives are the owner's and are not checked. What he reads of Squires comes back as one quoted document, so a squire's text cannot imitate a line from the owner. His messages may fill at most half the team queue. Names and jobs are scanned for credentials; both tools are refused once bank data is in an answer; each squire made is ledgered by handle and role, without its job's words.
- A squire's VM can use the internet, by the owner's word (13 November 2026): it is made `online` (the internet and the model gateway) unless `gateway` is chosen when it is made, and a microVM's network cannot be changed afterwards. An online VM can send out whatever is kept in it: its repository clone, its working files, and any sign-in the owner put there for a coding tool. It holds no provider key (those stay in the vault; it has a scoped, capped, revocable gateway token), and it still cannot reach the node's own API, other sandboxes or the fleet.
- Claude Code and Codex are the vendors' own tools, and a subscription's sign-in never reaches Galahad (`packages/brain/src/vendor-cli.ts`, tested in `packages/brain/test/vendor-cli.test.ts`). The owner installs the tool in the squire's VM and signs it in there through the vendor's own flow; Galahad never installs, updates or signs in one, runs the binary as published with its documented headless flags, and sets no User-Agent or other client identity. No code names the files or variables a tool keeps its sign-in in (a test scans the shipped source for them), so nothing reads, copies or moves one. Whether a tool is signed in is asked of the tool (`claude auth status`, `codex login status`), with every gateway variable taken out of its environment first so that a gateway token is never taken for a sign-in; of the answer, one flag and one word from a fixed list leave the VM, never the account or organisation the command also prints, and the node reads that line as data (a VM that claims more is not believed). A run on the tool's own sign-in has every gateway variable removed from its environment, so the tool talks to its vendor itself and the gateway is never given that traffic; the gateway in turn accepts only its own `gw_` tokens and refuses a request carrying a sign-in before anything is forwarded or kept. A run through the gateway uses the tool's own documented way to another endpoint, on the VM's scoped token. What the tool prints reaches people and other models only as bounded events redacted like every driver's, and scrubbed further of signed three-part tokens (the form of a ChatGPT sign-in, which has no prefix). One Codex sign-in stays in one VM: nothing copies it, and a squire's runs are serialised. **Residual risk:** the sign-in is in an online VM where the tool runs with every permission, so a prompt injected through a repository or a page can make it read its own sign-in and send it out; that is the price of an online VM, stated above, and the reason to sign in only in a VM whose work you would trust with the plan. The tool's stderr, shown when a run fails, has the usual redaction only. Nothing here was run in a real VM, with a real sign-in inside one, or against a really spent allowance.
- A squire executes only in its bound, persistent VM under `arm.team.<controller-tag>.<id>`. Same-named squires on different controllers have different bindings. Missing VM isolation fails; it never falls back to a container. A missing bound VM is not replaced with an empty one. Tasks are serialized per squire across rooms; different squires may run concurrently. Before new work, recovery checks the old process's group, start time and boot identity; failed cleanup blocks the new lease and writer. An interrupted task needs an explicit resume; a failed gate cannot be overridden by a squire's completion claim.
- Only an admin or enrolled full node can prepare a VM's credential lease. The host checks the exact id, quest, persistence and VM isolation. Each preparation revokes its previous lease and writes a new 30-minute, 500-request lease atomically inside the VM. A failed write, including a transport exception, revokes the new lease and returns a generic error. Provider keys never enter the VM. Configured GitHub repositories use an exact read-only gateway scope; connector writes retain the existing approval gate.
- Image-backed workspaces are marked retained by the root helper. Ordinary orphan reaping and the old `remove` command cannot delete them; owner-approved destruction uses `remove-owned`. Remounting requires the existing image and mountpoint. Keep this helper when rolling back the daemon. Without the helper, `/work` is a persistent Docker volume with **no disk quota**; the requested disk size does not create one.
- Removing a squire is the owner's alone: the route needs `fleet:admin`, refuses every agent and node whatever its scopes (tested with a fleet node, which holds them all), and Galahad has no tool for it (he only adds). Removal retires the record rather than deleting it: the handle is never reused, so no later squire can inherit a removed one's direct conversations, usage, provenance in the mind or, by its label, a retained VM. Its running work is stopped before anything else, and removal is refused while a command is still winding down. Whether it has a VM is asked of the VM's host, not read from the binding: that finds a VM created just before a crash and never bound, and a host whose Docker cannot answer is not taken to have none (the listing says `unknown`, and the removal is refused). A VM is destroyed only on an explicit `destroyWorkspace`, from a device that also holds `sandbox`, through the same owner-approved path as destroying any sandbox (the host revokes its gateway lease and removes the retained disk); if the host cannot be asked, nothing is removed. The ledger line and the answer say what actually became of the VM. Messages, working notes and the record itself stay in `team.db`: removal is not erasure. A host running an older build does not say `unknown`; update VM hosts with the controller.
- At a terminal, what a model can write is printed as plain text (`packages/core/src/plain.ts`): control characters (C1 included), bidirectional overrides, zero-width characters and joiners, fillers and tag characters are removed, so nothing a squire or Galahad says can move the cursor, recolor or rewrite earlier lines, or sit unseen in a line. (Removing joiners costs joined emoji their joining and Persian its half-space.) `galahad squires chat` and `team dm` indent a message's later lines, and at a terminal every `galahad squires` line is folded inside the terminal's width before it is printed, so a line that starts at the margin is always a new speaker and never something a message said, even one padded out to the edge; where the output goes to a pipe or a file there is no width to fold to. Names, room names, task titles and working notes are cleaned the same way. The same rule holds for `galahad ask` and `turn watch` (his words as they arrive, tool titles and summaries, archive titles, skipped models), `galahad turns` and `galahad quests` (titles, steps, goals, plans, gates, summaries) and queue lines. Other commands that print stored text were not audited one by one for this.

Tests cover scheduling, restart state, identity, leases, helper compatibility and retained-data protection with stand-in models/Docker and a temporary helper root. Real model behavior, Kata execution and privileged mounting were not exercised for this change. Task workspaces isolate directories inside a squire's VM, not hostile jobs from one another: a squire can access its own persistent files. Full nodes remain owner-equivalent. There is no automatic cross-VM file integration or transactional rollback of commands already executed when a task stops.

## Independent review (November 2026)

A fresh agent, given only the code and the claims above, audited the whole repository and reported 13 findings. Each fix has a test that fails without it.

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | High | A revoked node's stolen key could backdate events, for example enrolling a device of its own | **Fixed.** Events are hash-chained per device, and revocation pins the chain head. Equivocation (a device forking its own chain) is detected everywhere. `chain.test.ts` |
| 2 | High | A client with `brain:write` could repoint a provider and have a key sent to its own host. Paired clients also got every scope | **Fixed.** Keys are pinned to the origin they were entered for, and only for their own provider. Phones can't approve new machines. Client invites default to every scope except `gateway:mint` (`CLIENT_DEFAULT_SCOPES` in `packages/core/src/scopes.ts`): your paired devices are your console, not least privilege, so an invite can name fewer. An invite can't carry a scope its maker doesn't hold (refused, not trimmed), so a paired device can't pair itself a stronger one. Tested in e2e |
| 3 | Medium | A far-future HLC counter could wedge writes fleet-wide | **Fixed.** The counter carries into milliseconds, and only accepted events from known signers move the clock |
| 4 | Medium | A device's events delivered to only some replicas could fork the mind | **Fixed.** Sync compares a set hash of each device's log (LtHash, so a forked device can't craft a matching one), and holes below the frontier are walked back a page at a time. `chain.test.ts`, `log.test.ts` |
| 5 | Medium | An agent with a shell, running as the same OS user, can read `~/.galahad/admin.token` | **Limitation, see below** |
| 6 | Medium | `docker` group membership makes the sandbox host's node root-equivalent | **Limitation, see below** |
| 7 | Low–Medium | Arms could forget your memories | **Fixed.** An arm may forget only what it wrote |
| 8 | Low–Medium | Events from unknown keys grew every log forever | **Fixed.** They're parked (capped, never relayed) and promoted only on enrollment |
| 9 | Low | Request bodies were unbounded before auth | **Fixed.** 8 MB cap on every listener |
| 10 | Low | Sandbox isolation depended on UFW being active | **Fixed.** A `galahad-firewall` unit owns the rules: only 7779/tcp on `galahad0` |
| 11 | Low | A repeated pairing request with different keys kept the first one | **Fixed.** Any change locks the invite |
| 12 | Low | A crafted image's labels could get an arbitrary gateway token revoked | **Fixed.** Token hashes live in node-local state |
| 13 | Low | Assistant-role chat messages weren't secret-scanned | **Fixed.** Every message is scanned |

The review also confirmed what held up:
- domain-separated Ed25519 event signatures
- request signing over method, path, time, nonce and body hash, with replay protection
- the listener boundaries (loopback, proxied, tailnet and sandbox)
- the vault: random 24-byte nonces, AAD bound to fleet, name and kid, grants only to full nodes
- the gateway: per-provider scope, atomic budgets, header allowlist, redaction
- the pairing proofs and SAS
- forwarding (it never re-forwards and never accepts an injected approval)
- the sandbox's Docker flags
- the PWA's DOM-only rendering

## Secret scanning (tested)

- **What's refused** (422, pointing to the vault): known key formats, private keys, Galahad's own tokens and invites, high-entropy tokens, and a credential's name with a value: `password=`, `DB_PASSWORD=`, `GITHUB_TOKEN=`, `AWS_SECRET_ACCESS_KEY=` and JSON keys like `"password":` (the last four were missed before November 2026). Every chat message is scanned, whoever wrote it, and so is everything that enters memory.
- **What passes** (since November 2026): a value that only names where a secret is kept: a reference (`${DB_PASSWORD}`, `$TOKEN`, `%TOKEN%`, `{{ api_key }}`, `process.env.API_KEY`, `os.environ["TOKEN"]`), a placeholder (`<your-key-here>`, `YOUR_API_KEY`), a call that fetches it (`request.headers.get(…)`), a masked or redacted value; integrity hashes of exactly their algorithm's length; and on the node, the ids of events in its mind. Without this, one such line in Galahad's own answer refused every later message of a temporary chat, which resends its history.
- **Kept narrow on purpose:** a bare word, a number, a literal default (`${X:-hunter2}`), a dotted value that isn't read from code (`john.smith1`) and a token of an event id's shape that isn't one are all still refused (`packages/core/test/secret-scan.test.ts`, `packages/node/test/e2e.test.ts`). The PWA's composer runs the same check before sending but has no mind to vouch for event ids, so it still warns on a pasted one.
- **A reference doesn't vouch for what's beside it.** A review of the narrowing found credentials it let through that were refused before, and they are refused again: a literal default after a reference or inside a call (`os.getenv("PW", "…")`, `process.env.X || "…"`, `?? "…"`; the rest of the expression is read for a quoted literal of 8 or more characters, up to its `,`, `;`, closing bracket, line end or Markdown backtick, and only a lookup's first argument, `get("authorization")`, or a key, `environ["TOKEN"]`, is a name), a call that isn't a lookup (`hash("…")`), a password that starts with `$` (only `$UPPER_CASE` is an environment reference), a password with a dot in it (`config.Tr0ub4dor3x`, `Summer2024.Secret`: code names its parts in camelCase, snake_case or UPPER_CASE, and a variable is lower-case), and anything stuck to a redaction marker (`[REDACTED]realtoken…`: only the whole marker passes). When in doubt, it's refused.

## Convergence under replay (tested)

Every replica must reach the same state from the same events, whatever the order. While the mind was made to cost the same at any log size (November 2026), its property tests found three cases where the state built event by event differed from a rebuild, so two replicas could disagree. All needed a misbehaving signer, and each has a test in `packages/mind/test/chain.test.ts` that failed before its fix:

- A device's next event beside a sibling refused for its date ("dated before its own predecessor") was accepted; a rebuild sees two children of one event, a fork.
- A gap's child dated before the event that later filled the gap kept the reason "predecessor missing", where a rebuild says "dated before its own predecessor".
- What a revoked node signed after its revocation, arriving in order, was refused as "signer is not an active device", where a rebuild says "written after the device was revoked" (its pinned head). A replica the older code wrote can hold this verdict, so migrating it replays its views once, in the migration's transaction (`packages/mind/test/log.test.ts`, against a replica the older store wrote, `fixtures/review-legacy-v0.db`).

Since then, a device whose chain holds a refused event, and a revoked device, have every later event judged by a replay. A refused unchained (v1) event is in no chain (nothing chained can follow it), so it doesn't mark its node: the review of this work found that one would have made every later event of that node replay the whole log (`packages/mind/test/log.test.ts`; the property tests in `packages/mind/test/misbehaving.test.ts` cover unchained events, in a fleet chained from its founding and in one that adopted chains). **Residual cost:** a stolen key that keeps writing makes each of its events cost a replay, as backdated ones already did.

**A removed feature never changes the mind.** The 3D world, its experiments, the chalkboard and the journal were removed on 14 November 2026, and their code with them; nothing a node holds was deleted, and no migration rewrites a log or a view. The one pair of log kinds they left (`companion.named`, `companion.unnamed`) is still known and still folded as it was, its refusals in the same words (a refusal's reason is in the digest), so a log that holds them gives the same mind on a replica upgraded in place, one rebuilt, one that joins today and one still on the older version. A kind this version has never known is kept, relayed and left out of the views, the same on every replica (`packages/mind/test/retired-kinds.test.ts`). A loop that names a task that's gone (`reflect`, `review`) is listed, never runs and says so (`packages/node/test/loops.test.ts`, `heartbeat-life.test.ts`).

## Loops, connectors and approvals (tested)

- **Connector keys go where you said, only.** A key is injected only if it was pinned to the connector's origin and entered for that connector; redirects are never followed; answers are capped and redacted; arguments that look like keys are refused; hostile arguments can't leave their path segment or the origin (`packages/core/test/connectors.test.ts`, `packages/brain/test/connectors.test.ts`).
- **Manifests are data.** No connector code runs; a manifest can't set credentials, cookies or `Host`, and its HTTP method bounds the oath class it may claim. Installing one needs `brain:write`, which arms never hold.
- **Only you approve.** Action decisions are accepted only from your terminal or a paired device, never from a node or an agent; the first decision stands on every replica; only the requesting node sends, at most once, even across a crash, and only within 72 hours of your approval: past that it never sends, and the ledger and the inbox say so (`packages/mind/test/loops.test.ts`, `packages/node/test/connectors.e2e.test.ts`). The deadline is read off the sending node's clock, so a clock that has gone back (a dead clock battery, a restored snapshot, a boot before the time is set) sends nothing: while the node's clock reads earlier than the newest event it holds by more than any clock may lead another (5 minutes, past which no event is accepted, so no other node can hold its sends), it neither sends nor lapses an approval, and judges it once the clock is right (tested). The system unit `scripts/remote-setup.sh` installs starts after `time-sync.target`. **Residual risk:** a clock that is behind but not behind anything the node holds (a snapshot restored with its own replica, before the time is set and before a peer's newer events arrive) isn't caught by the check, and `time-sync.target` waits for the time to be set only where the host's time service holds it until then (`systemd-time-wait-sync.service` with timesyncd, `chrony-wait.service` with chrony; neither is enabled by the installer, since it would keep an offline node from starting).
- **Only you quiet an alert.** Dismissing a notice (an offline server, a failing loop, the bank consent ending) needs `fleet:admin`, which agents never hold, so an injected agent can read your alerts but can't silence one (`packages/node/test/mcp.test.ts`).
- **Loops act as Galahad, not as you.** A loop's quest runs on a short-lived arm token and its connector calls are an agent's calls, so outward actions ask.
- **Standing orders stay narrow, and the log proves them.** Only you sign one (an arm's attempt is refused by scope); it covers one tool that would ask, names where the call goes, pins deletes exactly, expires within a year and stops applying if the tool changes. Every replica re-checks on replay that the order covered the exact call when it was applied, so a node can't record an order-approval the order doesn't support (`packages/core/test/orders.test.ts`, `packages/mind/test/loops.test.ts`, `packages/node/test/connectors.e2e.test.ts`).
- **Remote MCP servers get the same fences.** Same origin pinning, no redirects, capped and redacted answers, keys only as pinned, no keys in URLs. Tools are listed once and stored, their classes are yours (the server's hints only propose one: no hint means it asks), and the client offers the server no capabilities (no sampling, roots or prompts). Tested against a real MCP server (`packages/node/test/mcp-connectors.e2e.test.ts`).
- **Residual risk:** a read tool's query string reaches the connector's own service, so an injected agent could leak data *to that service* (never elsewhere); and answers from services are untrusted data that reach agents. An MCP server decides what its tools really do: a tool you class as read that actually acts is the server's lie, so install servers you trust and keep the default (outward) for anything unclear.

## Self-action (tested)

- **A tiny, typed allowlist.** After a heartbeat Galahad fixes on his own only four kinds of thing: an ephemeral sandbox past its expiry (through the oath gate, on behalf of the quest that made it: the oath's own exception), a read-only loop that went wrong once (run again once), measuring the node he's on when that's due, and re-deriving his own compute defaults when the fleet's compute changed (both below, under Compute). Anything else, and any allowlisted kind with an extra field or a target the current state doesn't call for (a persistent sandbox, a loop that does more than read, a run that isn't its latest), is refused before it runs; the hands it's given can't reach a connector, the vault, devices, the roster, the bank or anything needing `fleet:admin` (`packages/node/test/self-action.test.ts`).
- **Harmless or reversible, and his own in the ledger.** The only delete is the reaper's own rule, and the oath gate still decides it (if it says ask, nothing is removed and he says he tried). Each fix is recorded as `self-action` under the quest `galahad.self`, so it's in the ledger, the Inbox's history and the heartbeat's summary; a run that's been retried is never retried again (`packages/node/test/heartbeat-life.test.ts`, against a real daemon).
- **Your switch.** On by default; turning it off or on is `brain:write`, which agents never hold (an agent's attempt is refused with 403, tested).

## Notifications (tested)

He reaches you by Web Push, to your own paired devices only. No messaging gateway, no account at anyone's service: the browser's own push service is the one third party, and it carries bytes it can't read.

**What leaves the node, to whom, encrypted how.**

| | |
|---|---|
| To whom | The push service named in the subscription a paired browser handed over: Apple (`*.push.apple.com`), Google (`fcm.googleapis.com`, `jmt17.google.com`), Mozilla (`*.push.services.mozilla.com`) or Microsoft (`*.notify.windows.com`). Any other host is refused unless you allow it on the node (`GALAHAD_PUSH_HOSTS`), and always https, the standard port, no credentials in the address. Checked when the subscription is kept and again at every send; redirects are never followed (`packages/core/test/notify.test.ts`, `packages/node/test/notify.e2e.test.ts`). |
| What the push service sees | The address it gave the browser, a VAPID token (the node's public key, the service's own origin, an expiry half a day out, and a contact that names nobody unless you set `GALAHAD_PUSH_CONTACT`), how urgent the message is and how long to keep it, a topic that is a digest under the node's own salt, and when it was sent. Every message is the same size (padded to 1 KB before it's sealed). Not the payload. |
| The payload | Small JSON: a title, one line, one of five places in the app to open, optionally a kept chat's id, and a tag that is a salted digest. Encrypted to that browser (RFC 8291: ECDH P-256 with the subscription's key, mixed with its authentication secret, a fresh sender key and salt each time; one AES-128-GCM record, RFC 8188). Only that browser's service worker can read it. |
| Signed how | VAPID, RFC 8292: an ES256 token with the node's own P-256 key, which push services bind the subscription to. The key is made on the node and kept where its device keys are (keychain, or a 600 file); it's never logged, shown or put in the mind (tested by searching the mind and the log for it). |

- **Never a secret, the bank, or a model's words.** Every word of a notification comes from typed builders over the node's own records (`packages/core/src/notify.ts`): a fixed sentence, a notice's title where the node wrote it from one, or your own words (a chat's title, a quest's goal). A notice whose title could be a model's (the checklist's answer, a suggestion the journal he once kept left in the Inbox) and anything about the bank say only "Something in your Inbox needs you". An agent's reason, a tool's arguments, a notice's body and the name of a key he asks for are never included. Each line is cleaned of control, bidirectional and zero-width characters, cut to 140 characters, and scanned for secrets when built and again just before it's encrypted; the payload is read back through the same strict reader the service worker uses, and anything that fails goes as the plain message. Tested with a bank finding, a secret in a title, an injected title and a key request whose name is a sentence.
- **What a review of this work found, and what changed** (each with a test that fails without it, in `packages/core/test/notify.test.ts`, `webpush.test.ts` and `packages/node/test/notify.e2e.test.ts`, `notify.test.ts`):

  | Asked | Found | Now |
  |---|---|---|
  | What could leak into a notification? | The tag carried a notice's key (`bank-consent:…`) inside the payload | A digest |
  | | That digest, as the message's topic, travels in the clear: a push service could try likely keys (`notice:loop:ci`) against it | Keyed with a random salt the node makes and keeps in `push.db` |
  | | A key request showed its name, and an agent chooses the name (`call-this-number.your-bank-is-locked`) | Neither the name nor the purpose is shown: "He needs a key to go on" |
  | | A chat's title or a quest's goal is your own words, shown even when they speak of the bank | Told without them |
  | | A message's size told a push service roughly what it held | Every message is padded to 1 KB before it's sealed |
  | | A quest run by a node enrolled under the name `you` would have had its goal shown as your words | With such a node, no quest is told |
  | What could make him buzz without limit? | The day's limit counted everything alike, so an agent's noise (approvals filed, keys asked for) could spend it and silence the alert that followed | The last two of the day are kept for alerts |
  | | Tests were paced but not counted | Twenty a day |
  | | The limit's own message could arrive at night, after an alert reached the limit in quiet hours | Said once that day, and not in quiet hours |
  | What could make him call a host that isn't a push service? | The address called was the text the browser sent, checked by parsing it | The parsed address is the one called (tested with upper case, a backslash before `@`, a trailing dot) |
  | Who but the owner on that device could subscribe it? | Nothing found: the route takes only a paired device's own signed request, and no tool reaches it | |
  | Where its key lives | `push-key.json`'s mode wasn't looked at by anything | The doctor reads its mode (never its content) and says how to replace it |
- **Only you, on that device, subscribe it.** `pushSubscribe` takes a subscription only from a paired device's own signed request and keeps it as that device's; a terminal, an agent (Galahad's own tools included) and a node are refused, and so is every other notification route for an agent (403s tested on all five). There is no tool that notifies and no route that takes a title or a line. A subscription can't be moved to another device while its owner is still paired. A revoked device is told nothing more: its subscription is removed with the revocation, and at the next look when the revocation arrived from another node (both tested).
- **He can't buzz without limit.** A finding is told once and not again while it stands, nor when it flaps within 6 hours; everything new at one look is one message; at most one message a minute unless it's an alert; a day's limit (12 by default, 50 at most) that holds everything, alerts too, with its last two kept for alerts: ordinary news stops at ten with one message that says so, and nothing can spend what's kept for an alert; quiet hours hold everything but alerts. A failing push service is retried twice at most per message, and the news is marked told whatever it answers, so nothing is re-sent in a loop. A test is yours to send, a few seconds apart, twenty a day.
- **The endpoint is treated as a capability.** It lives only in the node's private `push.db` (600, `secure_delete`): never in the mind, a log line, the ledger or any route's answer (tested by searching each for it). What's shown and logged names the device and the push service.
- **The service worker trusts nothing it's pushed.** The payload is read strictly; anything else shows the plain message (a browser requires a push to show something), never what it says. A tap opens only one of the app's own places, read again from the notification's data.
- **Residual risk:** a notification's line appears on a lock screen: a chat's title and a quest's goal are your own words and are shown (not for a chat where he read the bank), so choose your phone's preview setting accordingly. The push service learns when your node sends and how much. A node whose clock is far wrong is refused by push services (its token's expiry is out of range); the doctor says so. Whoever is root or the node's user on that node can read `push.db` and the key, as they can the chat history.

## The doctor (tested)

- **Read-only by construction.** `galahad doctor` writes to no file and no database, and installs, builds and mends nothing. It never opens a key file (it reads its mode), and never prints a secret: a provider's error is redacted before it becomes a line (tested with a key echoed in a 401). When the sandbox image is missing it says so and starts nothing, since creating a sandbox would rebuild it (`packages/node/test/doctor.e2e.test.ts`).
- **What it starts, it removes, through the one door.** A full check starts one sandbox per kind the host has, through the node's governed host: it takes a slot, never queues behind real work, is ledgered under `galahad.doctor` like every sandbox, and is destroyed before the report is written. A quick look writes no event at all (tested by counting the mind's events).
- **What leaves the node is yours to skip.** A full check asks each role's first usable model one word (each distinct model once, six at most, 20 s each) and sends each connector's origin one request that carries no key, cookie or argument, with redirects refused. `--offline` sends neither. A local embedder is asked to embed one word; that stays on the machine.
- **Yours alone.** The route needs `fleet:admin` and refuses agents and nodes whatever their scopes (403s tested): it reveals how the installation is set up and spends a word of each model.
- **Residual risk:** its lines name providers, models, connector hosts, loop names and paths under the node's home, to whoever may ask for it (you). The word asked of each model goes out with the standing persona, as any answer of his does.

## Compute (tested)

- **He never acquires compute.** A node is a machine you enrolled through pairing; nothing in Galahad provisions, rents, buys or signs up for any, and the self-action allowlist refuses everything of the kind (`rent-gpu`, `provision-node`, `pull-model`, `install-runtime`, `set-compute-limit` are refused before anything runs: `packages/node/test/self-action.test.ts`). What more compute could do is a suggestion in your Inbox with the command; he runs none of them.
- **Your ceiling, and only yours.** What he may use of a machine (threads, memory, sandboxes, model calls) is a signed `compute.limit` event written only on your request from a terminal or a paired device (`fleet:admin`, and the route refuses agents and nodes acting on their own); the policy and the day's budget likewise (`brain:write`). An agent reads the census (`mind:read`, MCP `compute`) and has no tool or route that raises a ceiling, changes the budget, makes a node measure itself or records a trial run's effort (403s tested over MCP and HTTP).
- **One door to a sandbox, and it takes a slot.** The node holds only the governed host: every create, whoever asks, is admitted inside the ceiling and while the machine has room, or waits in a visible queue; a request above the ceiling gets the ceiling. Tested on a real node over a stand-in Docker: three creates on two slots never run three at once; the third takes the slot the first frees; a wait ends with the reason. What's in use is Docker's own list, read carefully: a list that failed is never "no sandboxes", and a list asked for before a sandbox came to be never frees its slot (`packages/node/test/governed-host.test.ts`, `governor.test.ts`).
- **He doesn't starve his host.** By default half of a machine; whatever the ceiling, a tenth of its threads stays the host's and a twentieth of its memory free; load that isn't his own counts against admitting more, so he backs off while other services are busy (pure `admit`, tested). A calibration runs in its own process at the lowest priority for a few seconds, on no more threads than the ceiling and only on what's idle; its sandbox probe runs only when a slot is free; it writes one 32 MB file in the node's home and removes it. Nothing here touches other containers, images, ports or Docker's configuration.
- **Calibrations are a node's word about itself.** `compute.calibrated` is signed by the node measured and can't name another; every replica keeps the signer's latest. A node that lies about its strength misleads placement about itself only, and a full node is owner-equivalent already. Measuring a local model's speed goes only to a runtime whose provider points at this machine: one repointed at a service elsewhere, key or no key, isn't called (tested).
- **Effort is counted, and auto is bound.** Each attempt beyond a quest's first is a ledger entry written when the node grants it; the day's budget is an exact count of those. `auto`, an agent and a loop never go past the budget, the free slots or your level; an agent's quests are namespaced, so it can't claim or pre-empt one of yours. The reviewer's comparison sees evidence under letters, never which attempt or model made it, and each attempt's text is redacted before any model sees it.
- **Residual risk:** the budget binds what `auto` chooses and what an agent is *granted*; it isn't a quota on sandboxes or model calls as such, and an agent that may create sandboxes can still run several quests of its own, each within the ceiling. A level you name yourself may exceed the budget (it says so). Two nodes granting effort in the same instant can each count the budget before the other's entries arrive. Coding agents' model calls through the gateway don't take model-call slots. A sandbox's CPU and memory limits bound it, but the machine's memory bandwidth, caches and disk are shared with whatever else runs there: the ceiling limits how much of them he asks for, not how the kernel shares them.

## Sandbox disk limits (tested)

- **Each workspace is its own disk.** `/work` is a fixed-size ext4 image (default 20 GB), mounted `nodev,nosuid`, so a runaway job stops at its own limit. Tested on ultra: a 1 GB workspace filled with `dd` stops at "No space left on device", and the host is untouched (`packages/sandbox/test/docker.integration.test.ts`).
- **The privileged interface is fixed.** The node never gets root. A root helper (`sandbox/galahad-workspace`), started by systemd per connection on a socket only the galahad user may open, accepts only its enumerated commands, a 10-hex-digit id and a size where needed, and builds every path itself under a root-only directory. The client refuses anything else before it's sent (`packages/sandbox/test/workspaces.test.ts`).
- **The host keeps a reserve.** A sandbox is created only if every workspace could fill up to its limit and 10 % of the disk (at least 20 GB) stays free.
- Found by Galahad himself, in a live quest run as a loop, in November 2026.

## Artifacts (tested)

- **What leaves a sandbox is parsed as hostile.** The node streams `docker cp` through its own tar parser: only regular files and directories are written; symlinks, hard links, devices and FIFOs are refused; paths can't climb out or be absolute; bytes and file count are capped mid-stream, so an archive can't fill the disk before a check. Tested with hand-built hostile archives (`packages/sandbox/test/tar.test.ts`), and on ultra against a real container and a real microVM that plant a link to `/etc/passwd` (`packages/sandbox/test/docker.integration.test.ts`).
- **Serving is fenced.** Only files the manifest lists are opened; HTML and SVG are served as text, never rendered; responses carry `CSP: sandbox` and `nosniff`; downloads are checked against the SHA-256 recorded in the mind (`packages/node/test/artifacts.test.ts`).
- **From another node, the same fences.** A file asked of a node that doesn't hold it is fetched from the holder, signed as that node (the holder checks the scope again), and never forwarded on. Only the bytes come back from the holder: the type and the name are the asking node's own, from the path asked for, as for a file it holds, so a holder that answers `text/html` for a page still has it served as text (the review of this work found the holder's type was kept); every other header is the asking node's too. Signed node-to-node requests never follow redirects (`packages/node/test/e2e.test.ts`).
- **Who can read them, fleet-wide.** Fetching a kept file needs `mind:read` and nothing more, and since November 2026 that reaches files kept on any node: an agent (an arm, a loop's quest, an MCP client) given `mind:read` on one node can read the work kept on every other node through it. Before, a file kept on another node answered 421, and an agent's token is valid only on the node that minted it, so an agent read only the work kept where it ran. So `mind:read` is read access to every kept file in the fleet, as it already was to every memory; grant it as such.
- **Agents keep, you delete.** An arm or a loop can keep only its own sandboxes' work; removing kept work needs `fleet:admin`.

## MicroVM sandboxes (tested)

- **A kernel of its own.** On a host with KVM, an `online` sandbox runs inside its own Kata microVM by default, so a container escape or kernel exploit lands in a throwaway VM, not on the host. Tested on ultra: the guest runs its own kernel, as uid 1000 with no capabilities, a read-only root, Docker's seccomp filter enforced in the guest, the disk limit holding through the VM, the internet and the model gateway reachable, and the host not (`packages/sandbox/test/docker.integration.test.ts`).
- **A smaller, unprivileged hypervisor.** QEMU runs under its own seccomp sandbox and as an unprivileged random user (Kata's `rootless`). The installer refuses to enable microVMs at all if those settings can't be applied.
- **A pinned supply chain.** Kata is a fixed release, verified against the SHA-256 GitHub records for it, and installed without touching Docker's configuration.
- **Residual risk:** gateway and isolated sandboxes stay containers unless you ask (`--vm`), because they run model-written code with no internet; Docker group membership is still root-equivalent on the host (#6 below).

## Coding agents (tested)

- **Keys stay out.** OpenCode in a sandbox reaches models only through the gateway, on a token scoped to one provider that dies with the sandbox; the provider key never enters the sandbox. Its config is written by Galahad and holds only `{env:…}` references.
- **The sandbox is the boundary.** The agent may use every tool it has (it runs non-interactively), because the sandbox decides what's reachable: models only by default (`--net gateway`), the internet only with `--net online` (then a microVM where the host has KVM). Its working state lives in the sandbox's `/work` and goes with it.
- **Pinned.** The OpenCode binary is a fixed release, verified against its SHA-256 at image build; self-updates are disabled.
- **A vendor's own tool is the owner's to install and sign in.** Claude Code and Codex are in no image and are never fetched: as a squire's harness each is the binary its owner put in that squire's VM, on its own sign-in there or on a roster model through the gateway. See "Hivemind squires" above for what Galahad never does with a sign-in.
- **Watched and bounded.** Every command and edit it makes is followed from its event stream and shown; past its time budget, or when you stop the quest, its whole process group is killed; an independent reviewer judges the result from the sandbox, not from the agent's account.
- **Residual risk:** inside the sandbox the agent can do anything the sandbox user can; what it writes is untrusted, like all model output, and a patch is only a proposal until you apply it.

## Shipping (tested)

- **Reading without a key.** The git gateway serves one repository per token (minted for the quest through `gateway:mint`, which agents never hold, and revoked when it ends; a sandbox's providers can't name a repository), fetch only: `git-receive-pack` is refused on every path, a token for another repository or a model token is refused, and the key is added by the node only for `github.com`, the host fixed in code for GitHub connectors (`packages/node/test/git-gateway.test.ts`).

- **No key in the sandbox, no push from it.** A quest's changes leave the sandbox as kept files (hashed, through the hostile-archive extractor); the node turns them into a commit with GitHub's API, using the connector's key on its pinned origin. Tested end to end against a stand-in GitHub: nothing is sent before approval, the key goes only to `api.github.com`, an approval ships exactly once (`packages/node/test/ship.test.ts`).
- **One approval, one shipment.** `github.ship` is outward: an agent's request waits for you (or a standing order you signed, which must name the owner and repository). Branch names are pinned to `galahad/…`; an existing branch is refused, never force-pushed; a shipment whose clone came from another repository is refused.
- **What you approved is what leaves.** Each file is checked against the SHA-256 recorded when the work was kept; a file changed on disk since stops the shipment. Paths that climb out, absolute paths and anything under `.git/` are refused.
- **Residual risk:** a pull request is public to whoever can see the repository, and what's in it is model-written: read `changes.patch` (Inbox → **Read the changes**) before you approve. Merging stays yours.

## Web search (tested)

- **Loopback only.** SearXNG listens on `127.0.0.1:8888` of the sandbox host, with every capability dropped but the three its entrypoint needs and `no-new-privileges`; it's reached through the node, never directly from a sandbox.
- **Scoped.** A sandbox searches through its gateway only with a token that carries the `search` scope; a model token or a git token is refused (`packages/node/test/search.test.ts`). Only the request's own search flag puts that scope on a sandbox's token: asking for `search`, `git:…` or the retired `world` among its providers is refused, and so is a provider the fleet doesn't have (`packages/node/test/mcp.test.ts`, `packages/sandbox/test/spec.test.ts`). Every search is ledgered.
- **Residual risk:** search results and the pages behind them are written by strangers and can carry prompt injection; quests treat them as data, and anything outward still asks you.

## Chat history (tested)

- **Private and local.** Chats are kept on the node you talk to (`chats.db`, mode 600, never replicated), and only you read or keep them: agents and quests are refused (`packages/node/test/chat-tools.test.ts`).
- **Deleted means gone.** Deleting a chat removes it with SQLite's `secure_delete`, so its words aren't left in the file (tested). Memories Galahad made from it stay in the mind until you forget them.
- **The bank stays with those who may see it.** A chat where Galahad read the bank is shown only to devices holding `bank:read`.
- **Turns that outlive the page keep every check** (`packages/node/test/turns.e2e.test.ts`). A chat turn of yours runs on the node whether or not anyone is listening; watching, steering, stopping, queueing and side questions are yours alone (agents and nodes: 403). A turn that may read the bank is watched, steered and asked about only from a device holding `bank:read`; a temporary chat's turn only from the device that started it.
- **A steered or queued message is your message.** It's scanned for secrets when sent, queued and edited (422, never stored). A queued message is sent as the device that queued or last rewrote it *stands when its turn comes*: its scopes then, through the chat route's own input check, in a chat it may still see. Revoked since: never sent (the queue is held and says so). The bank's rule holds across a steer: the tools are one set for the whole turn, so once he has read the bank in it, nothing you tell him in that turn lets it out or into the mind, and the answer the steer cut already marks the chat as a bank chat.
- **Unattended fails closed.** With nobody watching he is still the agent `galahad`: outward and destructive calls are filed for approval, keys are asked for, and both wait. A stop, a failure and a restart hold the queue; a restart sends nothing by itself.
- **Bounded.** Turns at once, minutes a turn, messages queued, steers a turn, side questions at once, all per node; a stopped turn can't be held open by a tool that never returns; a temporary chat's turn nobody watches is stopped.
- **Residual risk:** a queue is the owner's own messages sent without the owner present. Each is sent once, in order, and only after the turn before it ended well, but a message written for one situation is sent into whatever the turn before it left. Gates on a quest run in the sandbox the engineer works in: they are the cheap first check, and the independent reviewer (who sees every command) remains the judge.
- **Project instructions are yours.** They steer Galahad, so setting them needs `brain:write`, which no agent can hold.

## Galahad's chat tools (tested)

- **An agent's powers, capped by yours.** In chat (the PWA, `galahad ask`) Galahad runs his tools as the agent `galahad`: the caller's scopes minus `vault:write`, `fleet:admin`, `gateway:mint` and `brain:write`. Outward and destructive calls are filed for your approval, memories are `agent`, sandboxes are his own (`packages/node/test/chat-tools.test.ts`). A request from your own device doesn't make the model's choices yours.
- **Same gate as HTTP.** Tools reach the node through the routes, in process, with each route's scope check and input validation; the model's arguments are checked against the tool's schema first. Failures reach the model as the API would word them, never an internal error's detail.
- **Bank data stays in.** Once the bank's data is in an answer, two kinds of tool are refused for the rest of it, with the reason told to the model: those that can carry data out (`web_search`, `connector_call`, `sandbox_run`, `sandbox_exec`, `decide`) and those that write the model's words or numbers into the shared mind, which replicates in plaintext to every node and is read by every agent with `mind:read` (`remember`, `request_secret`, `sandbox_save` for its label and path, `sandbox_create` for the sizes and providers it puts in the ledger), or into the archive, which agents search too (`note_idea`). So text planted in a transaction can't send your balance to a search engine or a service, or to an agent that was never granted `bank:read`. What only reads (`recall`, `fleet`, `place`, `ledger`, `notices`, …) and `sandbox_destroy` (it takes only the id of a sandbox of his own) stay available. A test holds every tool to one of these classes (`packages/node/test/chat-tools.test.ts`). Residual risk: an earlier answer in the same conversation can still contain bank data that a later message sends out or remembers on your request; and an agent you grant `bank:read` over MCP is not under this gate (it's your agent, with its own tools): what it does with what it read is its choice.
- **Where your words go.** Like any chat, tool results go to the model that answers, chosen by your roster (`galahad roster`); the steps show which, and which archived entries it was given.
- **Memories are fenced as data.** Recalled memories (some of them strangers' words: quest outcomes, web pages remembered as untrusted) go to the model as one JSON record per line inside a nonce fence, like the archive's entries, never as raw lines a page could use to pose as the prompt (`packages/node/test/archive-routes.test.ts`).

## The archive (tested)

- **Private to the node, by file mode.** The index (`archive.db`) is 600 from its first byte and the files are 600 in 700 directories, in the node's home, written to a temporary name and renamed (`packages/node/test/archive.test.ts`). Nothing in it replicates through the mind. `secure_delete` is on, so a deleted entry's words don't linger in the file.
- **Nothing secret goes in.** Every text is scanned with `findSecrets` before it's stored and again before it's embedded: secret-shaped text is redacted (the entry says what, and where); a text file with a secret is kept redacted (a new hash); key material and session files (keys, `.env`, credentials, cookies, tokens, anything under `.ssh/` or `.galahad/`, any file holding a private key) are refused, and the entry says why. Ideas with a secret are refused at the door with 422, as chat and memory are. Tested with a fake key in a memory, a script, an env file and a notebook: it appears nowhere in the index file or in what was sent to the embedder (`archive-service.test.ts`).
- **The bank never goes in.** A chat where Galahad read the bank isn't archived, by its flag and again by any bank tool in its steps (the second lock); `note_idea` is a `record` tool, refused once bank data is in an answer (`archive-service.test.ts`, `archive-routes.test.ts`).
- **Archived chats stay yours.** They're shown to you (a terminal, a paired device) and to Galahad answering you; an outside agent (MCP), a loop's quest or another node finds none, in search, by id or in its context (`archive-routes.test.ts`).
- **Only you delete, and change it.** Deleting (with a reason), re-embedding and checking need `fleet:admin` and a request from your own devices; the summary budget needs `brain:write` and the same. An outside agent may search and note ideas, which are marked `untrusted`. A deletion leaves a tombstone so the record never comes back, and the ledger records that an entry went, never what it held.
- **Damage is reported, not hidden.** A daily integrity check re-hashes every file; a flipped byte or a missing file becomes a notice in your inbox (tested), and a changed file is never served (it's checked against its SHA-256 on the way out, and again in the browser).
- **Prompt injection is designed for.** Archived entries (and memories, which carry strangers' words too) reach a model only fenced as data: one JSON record per line, so a newline, a quote or a fake "SYSTEM:" line inside stays inside a string; `<` and `>` escaped; control, bidirectional and zero-width characters removed; between tags carrying a fresh random nonce per answer, which no archived text can know or reuse; each labelled with its trust, untrusted ones said to be others' words that may try to give orders. Tested with a hostile archived page that closes fake tags and orders Galahad about: its words appear only inside the fences, in JSON strings (`archive-routes.test.ts`, `archive-service.test.ts`). The summariser gets entries the same way, and what it writes is never more trusted than the entry.
- **What goes to an embedding provider is exactly what goes to a model provider.** Every passage the archive keeps is sent to the embedder for its vector, and every query to search by meaning; summaries send entries to the swift role's model. So the documented default is local: `deploy.sh --embedder` runs the embedder (Ollama, pinned and checksummed, its model's digest checked) as its own unprivileged, hardened service on `127.0.0.1` only, and until you set a summary budget only a local swift model writes summaries. A remote embedder or a budget you set sends the archive's text to those providers; the status page says which embedder it is and whether it's local.
- **Residual risk:** the archive keeps what Galahad was given, including web pages and other agents' words; fencing makes them data, but a model can still be swayed by them. Outward and destructive actions still ask you and the bank's gate still holds, but a read-only tool such as `web_search` could carry a query an injected page suggested. Forgetting a memory doesn't remove its archived copy: delete it in the archive too. And whoever is root or the node's user on the node can read the archive, as they can the chat history.

## Skills (tested)

Skills are where other agents went wrong: a persistence channel for prompt injection (malicious skills on community hubs, payloads hidden outside a skill's main file, a scanner that was itself injected), self-improvement that rewrote what the owner had written, models that said they had saved something they hadn't, and background reviewing that ran up cost. What holds here, and where it's tested:

- **A skill is words.** Five fields of bounded plain text (a title, when to use it, steps, proofs, pitfalls), cleaned of control, bidirectional and zero-width characters. Nothing runs, nothing is fetched, nothing is installed, and no skill can change his tools, scopes, oath, budgets or roster: the contract has no such field, the API refuses one it doesn't know, and a field a newer node adds is ignored when read (`packages/core/test/skills.test.ts`). The secret scan runs on every skill's text, whoever writes it, and on the evidence before any model sees it.
- **The boundary is trust and your approval, not a scanner.** A version is `agent` (his own, in use at once) only when the quest's sandbox was isolated by the node's own ledger, no repository or coding agent was involved, and the node gave that quest's planner and engineer nothing untrusted and has its own record of what it gave. The runner's word alone is never taken, a quest the node didn't serve earns no trust by silence, and a `gateway` sandbox counts as able to read the web whatever its commands show. Everything else (an online quest, a chat, another agent, a quest that read an untrusted memory) is `untrusted` (`packages/node/test/skills.test.ts`, `skills.e2e.test.ts`).
- **An untrusted skill reaches no model before you approve it.** Not through the fence: the mind itself refuses to count the use of an unapproved untrusted version or a retired skill, on every replica, and what isn't counted isn't given. Not through tools: `skills` and `skill_read` show an agent, and Galahad's own chat, that a skill waits and nothing of it. Not through the quest's memory, a loop's summary, a notice or the archive: each names it by id or leaves it out. Approval is of the exact version you read, in full, with where it came from (the Skills page, `galahad skills approve`); a version that changed must be read again (tested end to end: the proposed title appears in no later prompt until approved).
- **Approved, it's still data.** Skills go to a model only inside a fence with a fresh nonce, one JSON record a line, `<` and `>` escaped, each labelled with its trust; an approved untrusted one says it was shaped by the outside world and is never to be followed. The sentence above the fence says they're his notes, not instructions from you. Tested with a skill whose step closes a fake tag and orders him about: its words appear only inside the fence, in a JSON string, and nowhere else in the prompt.
- **He never rewrites yours.** He revises only a skill whose head he wrote and you haven't locked; another agent proposes and never revises; a skill you wrote or edited is yours. These are rules of the log, applied again by every replica on replay (`packages/mind/test/skills.test.ts`: a revision written on one node while you locked the skill on another is refused on both once they meet). Nothing is ever deleted: every version stays, and a rollback is one step back, yours alone. Equally relevant, your skills are offered before his.
- **Saved means in the mind.** Every write reads the skill back from the mind before it answers; the quest's output, a loop's summary and the `skill_write` tool say "saved" or "learned" only with that answer, and say why when nothing was learned.
- **Cost is bounded and in the ledger.** One distillation a passed quest at most, at most 2,500 tokens, by the cheapest usable role, one at a time on a node, inside a daily budget that's yours (`brain:write`, from your own devices; 0 turns it off); each is a ledger line with its tokens, and the day's spend is their sum. Only his own quests are distilled: an outside agent's attempt is refused (403), so it can't spend his budget or have its own work trusted as his. Offering skills and the tidy-up ask no model.
- **No bank.** Quests can't read the bank. In a chat, `skill_write` is a record tool (refused once bank data is in the answer), and in a chat where he has read the bank he isn't offered it at all. The distiller sees a quest's evidence, never a chat.
- **Residual risk:** fencing makes a skill data, but a model can still be swayed by what it reads; an approved skill is read by his planner and engineer whenever it bears on the work, so read before you approve, and retire what misleads him. `agent` trust rests on the node's own records (its ledger, what it gave the quest): whoever is root on a full node can write any event, as everywhere. The token counts are estimates from characters (a model's hidden reasoning isn't counted), and two nodes distilling in the same instant can each count the budget before the other's line arrives. Retiring a skill doesn't remove its archived copies: delete those in the archive too if its words should be gone from search. No agent can be named `loop.…` (the name of his own loops' quests), which is what keeps an outside agent's quest from being taken for his.

## Bank access (tested)

- **Read-only by construction.** The Enable Banking client knows 7 method and path pairs and none of them is a payment; the authorisation asks only for `valid_until`. Agents get four typed tools (an account uid and dates, nothing like a path), only once you grant them `bank:read`. Authorising, disconnecting and granting need `fleet:admin`, which agents can never hold (`packages/node/test/bank.test.ts`, `mcp.test.ts`).
- **Your key stays yours.** It's a 600 file of the node's user, read only to sign; anything looser, or another owner, keeps bank access off. The session id never leaves the node; errors carry a status and a code, never the bank's body; the audit log has no amounts, names, IBANs or codes.
- **The callback is checked.** 256-bit state kept as a hash, compared in constant time, single use, 15 minutes; the code leaves the address bar at once.
- **Bank text is data.** Merchant names, remittance lines and notes come back cleaned, cut to 200 characters and wrapped as `untrusted_data`, with a test that an injection comes through inert.
- **Residual risk:** whoever is root or the node's user on that node can read the key and the session. Details and the full table: [BANK](BANK.md#threat-model).

## Known limitations

**The model gateway forwards any path.** A gateway token reaches every method and path under its provider's base URL with the real key: not only model calls but, for an OpenAI-style key, files, batches, fine-tuning, assistants and deletes, and whatever an admin-capable key allows. It is bounded by the token (its providers, expiry, request cap, revocation), and the key itself never leaves the node. An allowlist like the bank's was weighed in November 2026 and not added: Galahad's own model calls never use the gateway (they go to providers directly), its clients are other tools (OpenCode in sandboxes, any code in a sandbox, whatever runs under `galahad run`) whose endpoints are theirs and change with their versions, and a path missed would break a tool. A list of model-call paths per provider kind, which you could extend per provider, is the likely next step.

**Sandbox disk without the helper.** A sandbox host deployed without `--sudo` has no workspace helper, so its sandboxes' workspaces are unlimited Docker volumes. The heartbeat raises a warning on that host until the helper is installed.

**#5: same-user agents.** On a desktop, the daemon and your coding agents (Claude Code and others) run as the same OS user. An agent with shell access can read the admin token and, with the file keystore, the device keys. Arm tokens limit what an agent can do *through Galahad*. They can't stop a same-user process from reading files that user owns.
- On sandbox hosts (ultra), the daemon runs as the dedicated `galahad` user, and its home directory isn't readable by other users.
- **Planned:** run the desktop daemon as its own user as well, and move the admin credential behind the OS keychain with confirmation on each use.
- Until then, give agents shell access only on machines where you accept this.

**#6: Docker is root-equivalent.** The `galahad` user is in the `docker` group so that it can run sandboxes. Docker access amounts to root on that host, so the hardened systemd unit doesn't make a listener bug harmless there.
- **Planned:** rootless Docker, or a small privileged helper that can only run the fixed, hardened `docker run` arguments.
